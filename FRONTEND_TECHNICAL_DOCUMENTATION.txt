SECTION 1: PROJECT OVERVIEW
==================================================

Platform Type   : SEO-optimized blog platform + admin panel
Frontend Role   : Server-side rendered public blog, client-side admin SPA
Rendering Model : SSR + SSG + ISR for public pages, CSR for admin panel

Auth            : JWT access token (memory) + HTTP-only refresh cookie

-- lib/api/adminClient.ts --

Setup: Admin Axios instance
baseURL          : envConfig.apiUrl + '/api/v1/admin'
withCredentials  : true (send HTTP-only refresh token cookie)
timeout          : 15000ms
headers:
  Content-Type   : application/json

Request interceptor:
  - Attach accessToken from Redux store (authSlice) to Authorization header

Response interceptor:
  - On success (2xx): return response
  - On 401 error:
      → Check if request is NOT already a retry
      → Call POST /auth/refresh (via adminClient)
      → If refresh success:
          → Dispatch setAccessToken to Redux store
          → Retry original request with new token
      → If refresh fails:
          → Dispatch clearAuth action (logout)
          → Redirect to /login

Error normalization:
  - Extract response.data.message or fallback to 'Something went wrong'
  - Re-throw structured ApiError


-- lib/api/publicClient.ts --

Setup: Public Axios instance
baseURL          : envConfig.apiUrl + '/api/v1/public'
withCredentials  : false (No auth cookies needed for public access)
timeout          : 15000ms
headers:
  Content-Type   : application/json

Response interceptor:
  - On success (2xx): return response
  - Error normalization: Extract response.data.message or fallback

SECTION 8: AUTHENTICATION & REDUX ARCHITECTURE
==================================================

Access Token Storage:
  - Stored ONLY in Redux store via authSlice (in memory)
  - NEVER stored in localStorage or sessionStorage
  - Lost on page refresh → restored via /admin/auth/refresh call

Refresh Token:
  - Stored in HTTP-only cookie (set by backend)
  - Sent automatically with every API request (withCredentials: true)
  - Cannot be accessed by JavaScript

Auth initialization flow (every page load):
  1. App mounts → AuthProvider useEffect fires
  2. Call GET /admin/auth/me (with cookie attached)
  3. If 401: call POST /admin/auth/refresh
  4. If refresh success: dispatch setAccessToken, call /admin/auth/me again
  5. If refresh fails: user is unauthenticated, redirect to /login if on admin route
  6. If /auth/me success: dispatch setAuth(user), mark as authenticated

SECTION 13: STATE MANAGEMENT STRATEGY
==================================================

All states (server-fetched API data and client-only UI configurations) are fully unified under Redux Toolkit (RTK) using createAsyncThunk. This eliminates the need for TanStack Query entirely, providing a predictable, single source of truth for the entire Admin SPA.

--------------------------------------------------
State Architecture & Lifecycle
--------------------------------------------------

1. Store Structure:
   The store contains dedicated thunk-driven slices for all entities:
   - auth (Token, active profile, authenticating status)
   - blogs (Admin feed, public feed, current editor blog, metas)
   - categories (Categories lists, active taxonomies)
   - tags (Manually configured / popular taxonomies)
   - ads (Configuration scripts, placements)
   - analytics (Macro dashboard overview, specific blog metrics)
   - blogEditor (Unsaved dirty states)
   - ui (Global navigation elements)

2. Thunk Lifecycle Handling (Builder Pattern):
   For every createAsyncThunk, the slice's extraReducers handles three distinct builder states:
   - pending   : Set isLoading to true, clear previous error.
   - fulfilled : Update state items/details, save meta (if paginated), set isLoading to false.
   - rejected  : Set isLoading to false, capture and store error.message.


--------------------------------------------------
Caching, Fetching & Refetching Patterns
--------------------------------------------------

1. Caching & Stale Prevention:
   To mimic automatic cache checking, components read the lists or entity data directly from the Redux state via useAppSelector. If data is already populated, the component can skip dispatching the fetch thunk unless:
   - A forceRefetch flag is explicitly passed.
   - The component is mounting for the first time in a fresh navigation.
   - A thunk-based mutation (e.g. create, update, delete) has run.

2. Mutation & Invalidation equivalent:
   Whenever an API mutation occurs, the thunk action must be successfully completed before updating the local store state. To ensure state consistency:
   - Execute the thunk mutation, using `.unwrap()` to catch any HTTP/validator exceptions.
   - On mutation fulfillment, dispatch the refetch thunk immediately to sync state back with the server.

   Example:
   ```typescript
   const handleSave = async (data) => {
     try {
       // 1. Dispatch update mutation thunk and unwrap payload
       await dispatch(updateBlog({ id: blogId, payload: data })).unwrap()
       toast.success('Blog updated successfully')
       
       // 2. Invalidate/refetch to sync the list
       dispatch(fetchAdminBlogs({ page: 1, limit: 10 }))
     } catch (err) {
       toast.error(err || 'Failed to update blog')
     }
   }
   ```

--------------------------------------------------
getImageUrl utility
--------------------------------------------------

File: src/lib/utils/getImageUrl.ts

Input  : blog: Blog | BlogListItem
Output : { src: string, alt: string }

Logic:
  1. If blog.images exists and has length > 0:
     return { src: blog.images[0].cdn_url, alt: blog.images[0].alt_text ?? blog.title }
  2. Else if blog.og_image_url:
     return { src: blog.og_image_url, alt: blog.title }
  3. Else:
     return { src: '/placeholder.jpg', alt: blog.title }

Usage in components to avoid repetitive null-check chains


==================================================
SECTION 16: ERROR HANDLING
==================================================

--------------------------------------------------
Global error.tsx
--------------------------------------------------

Catches: Errors thrown in Server Components
Renders: "Something went wrong" with retry button
Log: console.error in development

--------------------------------------------------
API Error Handling Pattern
--------------------------------------------------

In Redux Thunks (Client API Calls):
  Unwrap the dispatched thunk promise and catch the error. Show toast with the normalized message.

In Server Components (SSR/ISR Fetchers):
  Wrap fetch in try/catch
  If 404 from API → call notFound()
  If other error → throw Error (triggers error.tsx)

In Admin mutations (e.g. Save, Delete):
  Use the .unwrap() pattern on dispatch:
  dispatch(mutateThunk(payload)).unwrap()
    .then(() => {
       toast.success('Action successful!');
       dispatch(fetchRefreshThunk()); // Refresh state
    })
    .catch((err) => {
       toast.error(err || 'Failed to complete action');
    })

--------------------------------------------------
Not Found Handling
--------------------------------------------------

Blog detail (/:slug):
  If API returns 404 → Next.js notFound() → not-found.tsx

Admin blog editor (/admin/blogs/[id]):
  If blog not found → redirect to /admin/blogs with toast error

SECTION 18: ISR REVALIDATION WEBHOOK
==================================================

File: src/app/api/revalidate/route.ts

Purpose: Triggered by backend (after blog publish/update)
to instantly invalidate ISR cache for specific pages

Method: POST

Auth: Check request header x-revalidate-secret === REVALIDATE_SECRET

Body:
  {
    type: 'blog' | 'category' | 'tag' | 'home',
    slug?: string
  }

Handler logic:
  if type === 'blog' and slug:
    revalidatePath(`/${slug}`)
    revalidatePath('/') (home may show this blog)
  if type === 'category' and slug:
    revalidatePath(`/search/category/${slug}`)
  if type === 'tag' and slug:
    revalidatePath(`/search/tag/${slug}`)
  if type === 'home':
    revalidatePath('/')

Returns: { revalidated: true, timestamp: Date.now() }

Backend integration:
  After blog publish/update → call this webhook
  Fire and forget (no blocking)

SECTION 19: ADMIN ROUTE GUARD PATTERN
==================================================

Layer 1: Next.js Middleware (middleware.ts)
  - Check refreshToken cookie existence
  - Redirect to /login if missing
  - Fast, edge-runtime check

  - On mount: try to restore session via /auth/me
  - If restore fails: redirect to /login
  - Shows loading spinner during initialization

Layer 3: API Interceptor (lib/api/adminClient.ts)
  - On 401 response: attempt token refresh
  - If refresh fails: clear auth + redirect to /login
  - Handles token expiry mid-session

Admin layout (/admin/layout.tsx):
  - 'use client'
  - Reads isAuthenticated from AuthContext
  - If not authenticated + not loading: redirect to /login
  - Renders Sidebar + AdminTopbar + children when authenticated
